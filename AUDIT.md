# Grammar and Zed extension audit

Snapshot: 2026-11-05. This is a targeted audit, not a complete language conformance review.
The five grammars and `undivisible/zed-extensions` had no open pull requests at the time of inspection.

## Findings

- **V — scanner recovered.** The fork's grammar and corpus were imported in `b0c52e8` without the scanner, leaving its original unrelated parser in place. The crates.io 0.0.4 package also omitted it. The matching MIT-licensed scanner was recovered from [nedpals/tree-sitter-v](https://github.com/nedpals/tree-sitter-v/blob/6a35f91228eac6456154435f12dd8c4f75b4c830/src/scanner.c); its token order matches the imported grammar. The parser and Rust binding now include it.
- **V — corpus disagreement explained.** The old parser passed 39 of 135 imported corpus cases. Regenerating the imported grammar with its matching scanner passes all 135 without changing expected trees. The mismatch was between the fork's pre-import parser and the upstream grammar/corpus, not a reason to blindly rewrite snapshots. Parser node shapes change for consumers; review queries and downstream users when upgrading.
- **V — highlight query.** The query referenced `builtin_type`, which did not exist in the old parser. The regenerated parser provides that node, so the capture is restored. A follow-up capture audit added float, raw-string and C-string highlighting and removed the whole-array bracket capture; Rust tests check compilation and representative captures.
- **HolyC — limited but exercised.** All 10 existing corpus cases passed and `queries/highlights.scm` compiled against the parser. The README already identifies missing classes, `extern`, preprocessor, and full declarators. The package metadata disagree about version and license; verify provenance before changing license declarations.
- **Crystal — class methods and coverage.** Valid `def self.hello` class methods failed because the grammar placed the receiver before `def`; a separate fix moves it after `def` and adds corpus coverage. The grammar lacks many constructs including Crystal's `if` expressions and modules. The repository previously had no Tree-sitter corpus cases; parsing the sample without errors does not establish semantic correctness. See the [Crystal class method reference](https://crystal-lang.org/reference/1.19/syntax_and_semantics/class_methods.html) and [control flow tutorial](https://crystal-lang.org/reference/1.5/tutorials/basics/50_control_flow.html).
- **Nim — procedure indentation improved, grammar remains very incomplete.** Procedure and function bodies now distinguish dedented statements, with corpus and incremental parsing tests. The grammar still lacks object types, control flow and nested blocks; its own `sample.nim` still errors at an object field. Indentation handling is limited to the supported body constructs, not a complete implementation of the [Nim manual](https://nim-lang.org/docs/manual.html).
- **LOLCODE — multiline comments fixed.** The grammar now scans multiline `OBTW … TLDR` comments and has corpus and Rust tests, following the [LOLCODE 1.2 specification](https://raw.githubusercontent.com/justinmeza/lolcode-spec/master/v1.2/lolcode-spec-v1.2.md). Its Rust binding exports an empty highlight query; `tree-sitter.json` advertises several bindings absent from the repository, and its MIT license metadata conflicts with the Cargo ISC declaration. Verify license provenance before changing it.
- **Bindings and queries are inconsistent.** Crystal and Nim declare Node bindings in package metadata but only Rust binding files are present. Neither ships a highlight query. V and HolyC expose highlight queries, while LOLCODE exposes an empty one. Audit actual consumer requirements before standardizing APIs.
- **Zed registry uses other grammars.** At the inspected `undivisible/zed-extensions` snapshot, [V](https://github.com/lv37/zed-v/blob/2fcc5728837e311402f815e355fc547e022e19f9/extension.toml) pins `lv37/v-tree-sitter` at `fe01bbcc`; [Nim](https://github.com/foxoman/zed-nim/blob/d73cee39935be827d753c85f98214d49fc73b5cf/extension.toml) pins `alaviss/tree-sitter-nim` at `897e5d34` and a separate format-string grammar; [Crystal](https://github.com/crystal-lang-tools/zed-crystal/blob/f6c173593433bd2be929a5cedf7b9088c666cfdc/extension.toml) pins `crystal-lang-tools/tree-sitter-crystal` at `2af0dc12` and a separate ECR grammar. There are no HolyC or LOLCODE entries in that snapshot. This establishes what those registry entries load, not whether other consumers use these forks. Wiring these forks into Zed would require maintained extension repositories, grammar pins, compatible queries, testing in Zed and an authorized registry submission.
- **Do not submit the fork-specific V and Crystal fixes upstream unchanged.** The pinned V grammar declares no external tokens and passes all 337 of its own corpus cases; its scanner is not missing. The pinned Crystal grammar already parses `def self.thing` in its `class method definitions` corpus case. Neither fork-specific defect has been reproduced in the Zed grammars.
- **Extension scaffolds.** The HolyC and LOLCODE grammar repositories contain `zed-extension/` scaffolds pinned to their grammar commits. Their TOML and highlight queries were checked locally, but the extensions have not been exercised in Zed or submitted to its registry.

## Verification limits

Tree-sitter CLI 0.25.10 was used for the parse, corpus and query checks. The 0.26.8 prebuilt CLI could not run on this orb's glibc. Rust was installed afterward; V and Crystal Rust tests were run. Zed itself was not built or exercised. Further syntax, highlight semantics, binding compatibility and consumer integration remain to be audited.
